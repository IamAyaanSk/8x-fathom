// Create a watch (webhook) for calendar events
// This calls Google's watch endpoint and provides your webhook URL

async function watchCalendar(accessToken: string, calendarId: string, webhookUrl: string) {
const response = await fetch(
`https://www.googleapis.com/calendar/v3/calendars/${calendarId}/events/watch`, {
method: "POST",
headers: {
"Authorization": `Bearer ${accessToken}`,
"Content-Type": "application/json"
},
body: JSON.stringify({
id: `unique-channel-id-${Date.now()}`, // Unique identifier
type: "web_hook",
address: webhookUrl, // Your webhook endpoint
expiration: (Date.now() + 7 * 24 * 60 * 60 * 1000).toString() // 7 days max
})
}
);
return await response.json();
}

Yes — that direction fits the product slice well, and it’s cleaner than keeping a full calendar mirror.

## Why it aligns

`AGENTS.md` already treats calendar as input for **recordable** calls: skip rows without `meetingUrl`, dispatch bots from scheduled start, and the library is **meetings** (upcoming + processed), not every calendar block. Right now you effectively store everything in `CalendarEvent`, then would still need a `Meeting` for bot/R2/highlights — two layers for one user-facing thing.

`CalendarWatch` should stay: it’s for Google `syncToken` + push notifications, not for “all events.”

## Suggested model (conceptual)

**Remove** `CalendarEvent`.

**Extend** `Meeting` with calendar fields you need for sync + UI + dispatch:

| Field                                                              | Role                                                                        |
| ------------------------------------------------------------------ | --------------------------------------------------------------------------- |
| `googleEventId`                                                    | Idempotent upsert; handle cancel/reschedule (`@@unique` per user or global) |
| `title`                                                            | List / detail UI                                                            |
| `scheduledStartAt` / `scheduledEndAt` (or `startTime` / `endTime`) | F5 scheduler: dispatch at `start − buffer`                                  |
| `meetingUrl`                                                       | Required at **create** time (eligibility filter)                            |
| `htmlLink`                                                         | Optional “open in Google Calendar”                                          |

**Drop** `calendarEventId` and the `CalendarEvent` relation.

Keep existing bot/processing fields: `baasBotId`, `baasStatus`, `processingStatus`, R2 keys, `shareSlug`, etc.

**Eligibility at sync** (same rules you have now, applied before insert):

- In sync window (e.g. next 7 days)
- `status !== 'cancelled'`
- `meetingUrl` present (your `extractMeetingUrlFromGoogleEvent` logic)
- Optionally: only `scheduledStartAt` in the future for “upcoming”; past rows only if `processingStatus === 'ready'` (library) — product call for F4

## Sync behavior (important)

On each Google event in incremental/full sync:

1. **Not eligible** → do nothing (or delete an existing **pre-dispatch** row if URL removed / event cancelled).
2. **Eligible** → `upsert` `Meeting` on `googleEventId` (or `userId` + `googleEventId`), updating **only calendar fields** (`title`, times, `meetingUrl`, `htmlLink`).
3. **Never** overwrite `baasBotId`, `baasStatus`, `processingStatus`, R2 keys, or summary on a normal calendar update.

On **cancelled** Google events:

- If `baasBotId` is still null → delete the `Meeting` (or mark `cancelled` if you add a flag).
- If bot already dispatched / in progress → don’t delete; optionally mark cancelled and let worker/bot logic handle it (F5/F6).

That replaces today’s `persistGoogleEvent` + future “create Meeting from CalendarEvent” step.

## API / product impact

- **`GET /api/v1/calendar/events`** becomes redundant; F4 should list **`Meeting`** (filter upcoming vs library by time + `processingStatus`).
- **`POST /calendar/sync`** stays; implementation writes `Meeting` rows instead of `CalendarEvent`.
- **`GET /calendar/status`** unchanged (OAuth scope only).

Update `AGENTS.md` data model and F3 docs so they don’t mention `CalendarEvent`.

## Tradeoffs

**Pros:** One source of truth for the UI and worker; smaller DB; matches “we only care about meetings we can join.”

**Cons:** You can’t show “all calendar events” without another store (you said you don’t want that). Debugging “sync ran but nothing appeared” means “no eligible events in window,” not an empty `calendar_event` table.

## Scope note

This is a **schema + F3 sync refactor** and sets up **F4/F5** (list + dispatch query `Meeting` by `scheduledStartAt` and `meetingUrl`). It’s a breaking migration if you already have `calendar_event` data (merge into `meeting` or drop in dev).
