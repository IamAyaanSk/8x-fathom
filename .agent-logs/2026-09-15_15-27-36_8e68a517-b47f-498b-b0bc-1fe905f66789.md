### Why Baas webhooks looked “stopped”

The main bug was **Svix verification**: MeetingBaas sends `svix-id`, `svix-timestamp`, and `svix-signature`, but the `svix` `Webhook` helper (Standard Webhooks) verifies against **`webhook-id` / `webhook-timestamp` / `webhook-signature`**. We were passing the Svix header names directly, so **every request failed verification and returned 401**. Baas/Svix treats that as failed delivery (retries, then failures in their dashboard).

**Fixes in** [`meeting-baas-webhook.ts`](apps/server/src/services/meeting-baas-webhook.ts):

- Map Svix headers → Standard Webhooks names before `verify()`.
- Normalize `MEETINGBAAS_WEBHOOK_SECRET` (add `whsec_` if missing).
- Log reject reasons (`missing_svix_headers`, `invalid_signature`, `invalid_secret`) and log accepted event types.

**What you should confirm in MeetingBaas:**

1. **Account webhook URL** = `https://<your-ngrok>/api/webhooks/meetingbaas`  
   Per-bot `callback_config` only covers **terminal** events; **`bot.status_change`** needs the account webhook.
2. **`MEETINGBAAS_WEBHOOK_SECRET`** = the **Svix signing secret** from the dashboard (your value is fine; we now accept it with or without `whsec_`).

`Webhook.verify()` from the `svix` package **does not return the payload**. It only checks the signature and its return type is literally `undefined` — it calls the inner verifier with `jsonParse: false` and returns nothing.

That’s expected, not a bad secret. After `verify()` succeeds, parse the body yourself:

```ts
new Webhook(secret).verify(rawBody, { 'svix-id': ..., ... })
return JSON.parse(rawBody)
```

The handler now does that, normalizes the secret with a `whsec_` prefix when needed, and drops the debug `console.log`s. Webhooks should reach your Zod schema and `applyMeetingBaasWebhook` again.

### `hasMeetingBotJoinedCall` ([`baas-bot-status.ts`](packages/api-contract/src/baas-bot-status.ts))

Treats the bot as having joined if:

- `recordingStartedAt` is set, or
- `baasStatus` is anything other than **joining** or **failed-to-join** (in-call, post-call, completed, failed processing, etc.)

### Dispatch guards ([`bot-dispatch.ts`](packages/meeting-dispatch/src/bot-dispatch.ts))

- **`_assertNoPriorBotJoin`** — throws `409 A bot already joined this meeting` before schedule/capture/retry.
- **Row locks** (`_lockMeetingRow`, `_lockNextDueMeetingRow`) — only rows with `recordingStartedAt IS NULL` and `baasStatus` null or a **failed-to-join** status (so the worker won’t dispatch again after a completed/joined call).
- **Retry** — still only after failure, but **`failed_processing` is blocked** explicitly (`Bot cannot be retried after joining the call`). **Try again** remains for **failed-to-join** only.

So a calendar event that already had a bot join won’t get another `createBot`; only pre-join failures can be retried.
