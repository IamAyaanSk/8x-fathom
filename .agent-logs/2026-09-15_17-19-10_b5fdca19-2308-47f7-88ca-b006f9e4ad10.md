Bot lifecycle is now driven from one place in `packages/api-contract/src/baas-bot-status.ts`.

### State model (single source of truth)

| Stage                                    | `baasStatus` / events                               | `processingStatus`                    | UI phase                        |
| ---------------------------------------- | --------------------------------------------------- | ------------------------------------- | ------------------------------- |
| Not dispatched                           | `baasBotId` null                                    | `idle`                                | Starting soon                   |
| Joining / waiting room                   | `queued`, `joining_call`, `in_waiting_room`, …      | `idle`                                | Joining… / **In waiting room…** |
| Recording                                | `in_call_recording`, …                              | `idle`                                | In call — recording             |
| Post-call (Baas)                         | `call_ended`, `recording_succeeded`, `transcribing` | `processing` when `transcribing`      | Call ended, processing…         |
| `bot.completed` webhook                  | `completed`                                         | **`pending`** (transcription handoff) | Call ended, processing…         |
| Failed join (`bot.failed` / join errors) | failed-join enum                                    | `idle`                                | Failed to join → **Try again**  |
| Library ready                            | any                                                 | **`ready`**                           | Ready                           |

`getMeetingBotUiPhase` no longer treats `completed` as Ready; Ready comes from `processingStatus: ready` (F7 worker).

### Dispatch rules (`canDispatchNewBot`)

- **Early capture**: API sends bot; active bot returned if join/recording/processing is in progress.
- **Retry**: Only after **failed join**, meeting not ended, and **not** in the 2‑minute pre-start window (same as capture).
- **Worker**: Only rows with `baasBotId` null, `processingStatus = idle`, no `recordingStartedAt`, and failed-join or null status. Early-finished meetings keep a bot id and/or `pending`/`processing` → **never scheduled again**.

### Webhooks & polling

`patchFromBaasStatusChange`, `patchFromBaasCompleted`, and `patchFromBaasFailed` are used by both the **webhook handler** and **worker status poll** so transitions stay aligned.

Removed: `hasMeetingBotJoinedCall` and ad-hoc webhook merge logic.

### UI

Status label uses `getMeetingBotUiLabel(phase, baasStatus)` so **In waiting room…** shows for `in_waiting_room` / `in_waiting_for_host`.

Failed-join now goes through the same capture/dispatch path. The separate retry API is gone.
