`bot.completed` now matches the [v2 payload](https://docs.meetingbaas.com/api-v2/reference/webhooks/botwebhookcompleted): signed `video` and `transcription` URLs, plus extra fields ignored via `.loose()`.

On that event the handler looks up the meeting, skips if `baasStatus` is already `failed`, then:

1. Sets **`baasStatus` to `completed`**
2. Parses the object key from the signed **`video`** URL → `recordingR2Key`
3. Parses the object key from the signed **`transcription`** URL → `transcriptR2Key`

Query strings (signatures, expiry) are dropped. If the path starts with your `R2_BUCKET`, that prefix is stripped so the stored value is the object key S3/R2 expects.

Example: `https://….r2.cloudflarestorage.com/my-bucket/bots/abc/recording.mp4?X-Amz-…` → `bots/abc/recording.mp4`.

No extra util package — key extraction lives next to the webhook handler.

The 401s are **not** a payload/schema bug. MeetingBaas is reaching your server; **Svix signature check is rejecting every request.**

I inspected the ngrok traffic:

- `POST /api/webhooks/meetingbaas` is hitting Express (our JSON `Unauthorized` body).
- Headers are present: `svix-id`, `svix-timestamp`, `svix-signature`.
- Body is valid JSON (`bot.status_change` with your `extra.meetingId`).
- Replaying a captured request against `MEETINGBAAS_WEBHOOK_SECRET` fails with **`No matching signature found`**.

That means the secret in `apps/server/.env` is **not** the signing secret for the webhook endpoint currently sending to this ngrok URL. Common cases: API key pasted instead of the Svix `whsec_…` secret, or the secret from an **old** endpoint after the ngrok URL changed.

Fix:

1. In the [MeetingBaas webhook settings](https://docs.meetingbaas.com/api-v2/getting-started/webhooks), open the endpoint whose URL is  
   `https://<current-ngrok>/api/webhooks/meetingbaas`
2. Copy that endpoint’s **signing secret** (`whsec_…`).
3. Set `MEETINGBAAS_WEBHOOK_SECRET` to that value and restart the API server.

I also moved request logging **before** the webhook route and log reject reasons (`missing_svix_headers` / `invalid_signature`). After restart you should see `invalid_signature` until the secret matches; then those POSTs should be `200`.
