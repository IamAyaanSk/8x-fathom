Here is a focused review of the worker slice (`apps/worker` plus the dispatch/status contracts it depends on). I treated “logical error” as behavior that can leave meetings in the wrong state, duplicate work, or never reach `ready` / `failed` when the product says they should.

---

## Architecture (what the worker does)

Three cron loops (plus immediate run on boot):

1. **Dispatch** — `@repo/meeting-dispatch` `dispatchDueMeetings`
2. **Status poll** — `runActiveBotStatusSync` for in-flight bots
3. **Pending processing** — lock rows → `processMeetingArtifacts` (chat → summary/action items → embeddings → `ready`)

That matches F5 + F7. The weak spots are mostly **concurrency**, **terminal/failure handling**, and **dependencies on server webhooks + R2 keys**.

---

## High severity

### 1. Same meeting can be processed concurrently

`_lockPendingMeetingRows` re-selects meetings already in `processing` when any artifact column is still null. The row lock is released when the pick transaction ends; `processMeetingArtifacts` runs **outside** that transaction.

```15:37:apps/worker/src/process-pending-meetings.ts
    WHERE (
      m."processingStatus" = 'pending'::"ProcessingStatus"
      OR (
        m."processingStatus" = 'processing'::"ProcessingStatus"
        AND (
          m.summary IS NULL
          OR m."actionItemsExtractedAt" IS NULL
          OR m."chatMessagesIngestedAt" IS NULL
          OR m."transcriptEmbeddingsExtractedAt" IS NULL
        )
      )
    )
    ...
    FOR UPDATE OF m SKIP LOCKED
```

A second worker process (or a slow first run + next cron tick after the lock is gone) can pick the **same** `meetingId` while the first is still in `_runSummaryStep` / `ingestMeetingEmbeddings`. That causes duplicate LLM/embed calls and races on `deleteMany` + `createMany` (action items, chat, chunks).

**Expected fix direction:** only claim `pending` in the lock transaction, or keep an exclusive “lease” until the pipeline finishes (e.g. `processing` + `processingStartedAt` / advisory lock), or use `FOR UPDATE` held for the whole job (usually not ideal with long AI calls).

---

### 2. `processing` can stall forever — `processingStatus: 'failed'` is never set

Every artifact step catches errors, logs, and returns. `tryMarkMeetingProcessingReady` only promotes to `ready`. A repo-wide search shows **no** code path sets `processingStatus` to `failed`.

If transcript is missing, summary/embeddings fail, or embeddings never succeed, the meeting stays **`processing`** indefinitely. The UI contract in `AGENTS.md` describes `failed_processing`, but the worker never implements it.

Related stuck cases:

| Condition                                 | What happens                                                                                                                            |
| ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `bot.completed` without `transcriptR2Key` | Summary skipped, embeddings skipped; `summary` / `actionItemsExtractedAt` / `transcriptEmbeddingsExtractedAt` stay null → never `ready` |
| Transcript JSON with no usable utterances | `formatMeetingBaasTranscriptTextFromJson` / `buildTranscriptEmbeddingChunks` throw → steps abort → same stall                           |
| Persistent LLM/R2 errors                  | Retries every 5 minutes but status stays `processing`, not `failed`                                                                     |

Chat is handled sensibly when there is no file (`chatMessagesIngestedAt` set without R2). Transcript paths are not.

---

### 3. Post-call AI pipeline only starts from server `bot.completed` → `pending`

The worker never sets `processingStatus: 'pending'`. That only happens in `applyMeetingBaasWebhook` on `bot.completed` (server).

Status poll can advance `baasStatus` (including toward `completed`) but **does not** set `pending` or R2 keys. If account webhooks are misconfigured or `bot.completed` is missed, you can end up with a “done” bot in Baas and **no worker pickup**, even though README says polling helps “without webhooks” for **UI status** — not for F7 ingest.

This is a cross-service gap, but it directly affects whether the worker ever runs.

## Medium severity

### 4. Action items are skipped when summary fails (even if transcript is fine)

After summary, `_runTranscriptArtifactSteps` bails out if `summary` is still null:

```160:166:apps/worker/src/process-meeting-artifacts.ts
  if (
    !afterSummary ||
    afterSummary.summary === null ||
    afterSummary.actionItemsExtractedAt !== null
  ) {
    return
  }
```

Action items do not depend on summary in the AI layer (`generateMeetingActionItems` only needs transcript). A summary failure blocks `actionItemsExtractedAt`, which blocks `ready`. That may be intentional ordering, but it is stricter than the data model (independent nullable fields).

---

### 5. Status poll stops when calendar `endTime` has passed

```15:22:apps/worker/src/sync-active-bot-status.ts
    where: {
      baasBotId: { not: null },
      endTime: { gt: now },
      OR: [
        { baasStatus: null },
        { baasStatus: { notIn: TERMINAL_BAAS_STATUSES } }
      ]
    },
```

Meetings that run past scheduled `endTime` (common) fall out of the poll set while still `joining` / `in_call_recording`. If webhooks are weak, `baasStatus` can lag until `endTime` — then polling stops and state freezes unless a webhook arrives.

`TERMINAL_BAAS_STATUSES` includes `transcribing`, so poll also stops there; you rely on `bot.completed` for R2 keys and `pending`. That is coherent if webhooks are reliable; fragile if not.

---

### 6. Status poll does not pass recording start time

`patchFromBaasStatusChange` can set `recordingStartedAt` from `recordingStartTimeSec`, but the worker only passes the status string from `getBotStatus`, not a start time. `recordingStartedAt` may only be set via webhooks. Ongoing-call elapsed time (F6) can be wrong when polling is the primary path.

---

### 7. Dispatch cron `*/90` on the seconds field

```1:1:apps/worker/src/constants.ts
export const DISPATCH_CRON_EXPRESSION = '*/90 * * * * *'
```

With a 0–59 seconds field, `*/90` effectively matches second `0` only (~once per minute), not every 90 seconds. Probably not what you intended for “dispatch every 90s”.

## Lower severity / operational

### 8. Long `createBot` inside a DB transaction (dispatch package)

`dispatchDueMeetings` / `_dispatchLockedMeeting` call MeetingBaas **inside** `prisma.$transaction`. The worker inherits that. Under load or slow Baas, this holds row locks and risks transaction timeout (120s), not incorrect state by itself, but it can reduce dispatch throughput and cause spurious dispatch errors.

### 9. `callbackBaseUrl` / `webhookSecret` passed into dispatch but unused

In `bot-dispatch.ts`, `callback_config` is commented out; README documents **account-level** webhook URL instead. Not a worker bug if dashboard is configured, but `scheduler._dispatchCallbackParams()` suggests per-bot callbacks — easy to misconfigure and think dispatch wires webhooks.

### 10. Embedding ingest: one API call per chunk, serial loop

Correct but slow for long meetings; combined with batch size 3 and 5-minute cron, backlog can grow. Logic is fine; capacity is the concern.

### 11. Dev vs prod embedding dimensions

DB migration moves `vector` to **1024**; contract enforces 1024. Dev uses LM Studio `text-embedding-qwen3-embedding-0.6b` — if it returns another dimension, ingest throws, meeting stays in `processing` (ties back to #2).

### 12. `processMeetingArtifacts` order

Chat → summary/action items → embeddings is reasonable. Intermediate `tryMarkMeetingProcessingReady` calls are harmless no-ops until all gates pass.

---

## What looks solid

- **Chat ingest idempotency** and “no chat file → mark ingested” so chat does not block `ready`.
- **Action items replace** in a transaction (`deleteMany` + `createMany` + `actionItemsExtractedAt`) when a single run completes.
- **Embeddings replace** similarly; dimension check before insert.
- **Ready gate** is explicit and consistent in `meeting-processing-ready.ts`.
- **Scheduler** `noOverlap: true` avoids overlapping ticks of the _same_ cron job on one process.
- **Re-pick incomplete `processing` rows** is the right _idea_ for retries; the bug is doing it without an exclusive lease.

---

## Suggested priority if you fix

1. Exclusive processing lease (stop double runs).
2. Terminal failure or timeout policy (`failed` or re-queue rules) when required artifacts cannot be produced.
3. Align poll window with real bot lifetime (not only `endTime > now`) and/or reconcile `completed` without `pending` when webhook is missing.
4. Decide whether action items must wait on summary; if not, run them when `actionItemsExtractedAt` is null regardless of `summary`.
5. Fix dispatch cron expression if you want true 90s cadence.
