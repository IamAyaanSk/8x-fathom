The Vercel failure comes from how **Turbo orders tasks** and how **`@repo/db` resolves the Prisma client**, not from “Prisma missing on Vercel.”

## What the log is showing

During `turbo run build --filter=web`, Turbo schedules **`@repo/db#build`** and **`@repo/db#db:generate` at the same time**. Your snippet matches that: `build` fails with TS2307 while `db:generate` is still finishing and prints “Generated Prisma Client to `./generated/prisma`”.

`@repo/db#build` runs only `tsc`:

```25:25:packages/database/package.json
    "build": "tsc"
```

It does **not** run `prisma generate`. Generate lives in a separate task:

```17:17:packages/database/package.json
    "db:generate": "prisma generate && tsc",
```

## Why Turbo runs them in parallel

In `turbo.json`, `build` depends on **`^db:generate`** (generate in **dependency** packages), not on **`db:generate` in the same package**:

```49:52:turbo.json
    "build": {
      "dependsOn": ["^build", "^db:generate"],
```

For `@repo/db#build`, Turbo only waits on `@repo/typescript-config#build` / `#db:generate`. It does **not** wait on `@repo/db#db:generate`.

Web pulls in `@repo/meeting-dispatch`, which depends on `@repo/db`, so the web build graph includes both `@repo/db#build` and `@repo/db#db:generate` — without an edge from the latter to the former.

Locally this often “works” because `packages/database/generated` (and sometimes `dist/generated`) already exist from earlier `db:generate` / dev. On Vercel the clone is clean and **`generated/` is gitignored**, so the first `tsc` in `build` hits a missing client.

## Why TypeScript looks for `#generated/prisma/client`

Source imports the generated client via a subpath:

```3:3:packages/database/src/client.ts
import { PrismaClient } from '#generated/prisma/client'
```

That alias is wired to **`dist/generated`**, not Prisma’s output folder:

```6:8:packages/database/package.json
  "imports": {
    "#generated/*": "./dist/generated/*.js",
```

Prisma writes to **`generated/prisma`** (see `schema.prisma` `output = "../generated/prisma"`). Until something puts the client under **`dist/generated/prisma`** *and* `@repo/db#db:generate` has finished, `tsc` reports exactly the error you see.

Your leading `turbo run db:generate && …` helps only for the **first** Turbo invocation. The **second** one (`build --filter=web`) can still race `@repo/db#build` vs `@repo/db#db:generate` unless the graph or `@repo/db`’s `build` script fixes ordering.

## What to change (minimal)

1. **Serialize `@repo/db` build after generate** — either globally:
   - `"build": { "dependsOn": ["^build", "^db:generate", "db:generate"] }`  
   (Turbo no-ops `db:generate` on packages that don’t define it), **or** a `packages/database/turbo.json` override so only `@repo/db#build` depends on `@repo/db#db:generate`.

2. **Make `@repo/db`’s `build` self-sufficient on CI** — e.g. `"build": "prisma generate && tsc"` (and drop duplicate `tsc` from `db:generate` if you want), so a lone `build` task never runs `tsc` without generate.

3. **Align runtime imports with Prisma output** — either map `#generated/*` to `./generated/*.js` and copy/sync into `dist` for Node, or add a small post-generate step so `dist/generated` exists before `tsc`. Right now compile-time resolution targets `dist/generated`, while generate writes to `generated/`.

Also ensure **`DATABASE_URL`** (or `DATABASE_URL_UNPOOLED`) is set in Vercel for the build; `prisma.config.ts` uses it for the CLI. Your log shows generate succeeding, so env was fine for that run — the main issue is still **parallel `build` vs `db:generate`**.

| Layer | Uses `@repo/db`? |
